> "비용 절감은 아키텍처의 부산물이어야 한다. 무조건 싼 모델로 깎아내리는 것은 국소 최적화에 불과하며, 명확한 인터페이스 분리와 슬라이스 위임이 선행될 때 비로소 품질 저하 없는 비용 절감이 가능해진다."

대규모 언어 모델(LLM)을 코딩 에이전트와 실무 개발 파이프라인에 적극 도입하면서 가장 먼저 맞닥뜨리는 현실적인 벽은 **비용과 지연 시간(Latency)**, 그리고 **품질의 밸런스**입니다.

매 턴 최고 수준의 추론 모델(Anthropic Claude의 Fable, OpenAI Codex의 Astra 등)을 호출하면 코드 품질은 확보될지 몰라도 API 비용이 기하급수적으로 증가합니다. 반대로 경량 모델만 일괄 사용하면 복잡한 엣지 케이스나 아키텍처 설계에서 오류를 범해 결국 개발자가 개입하여 재작업하는 비용이 더 커집니다.

이 문제를 해결하기 위해 많은 개발자가 [OpenRouter](https://openrouter.ai/) 같은 통합 중계 서비스를 활용합니다. OpenRouter 생태계에는 복수의 모델 간 동적 라우팅, 가성비 모델 자동 배정 기능이 이미 널리 쓰이고 있기 때문입니다.

하지만 **저희 엔지니어링 팀은 주력 AI 모델 공급처가 OpenRouter가 아닙니다.** 각 AI 모델 공급자(Anthropic, OpenAI, Google 등)의 직접 API 및 전용 엔드포인트 플랜을 주력으로 사용하고 있습니다. 

따라서 OpenRouter 중심의 기성 라우팅 솔루션을 그대로 사용할 수 없었고, 자연스럽게 **"공급자 직결 환경이나 로컬 코딩 CLI에서도 유연하게 모델 비용을 최적화해 줄 대안 라우팅 도구는 없을까?"**를 탐색하게 되었습니다.

그 과정에서 발견한 것이 Claude Code 및 Codex CLI 환경에서 모델을 동적으로 낮춰준다는 오픈소스 로컬 프록시 라우터, **[jev-router](https://github.com/gargpratyush/jev-router)**(MIT)였습니다.

결론부터 말씀드리면, 저희는 소스 코드와 동작 메커니즘을 면밀히 분석한 끝에 **jev-router를 실제 개발 환경 및 에이전트 파이프라인에 도입하지 않기로 결정했습니다.**

이 글에서는 jev-router의 내부 작동 원리와 배울 만한 점을 짚어보고, 그럼에도 불구하고 저희가 이를 채택하지 않고 자체적인 **슬라이스 위임 및 실측 게이트 아키텍처**를 고수하게 된 기술적 근거와 현실적인 트레이드오프를 공유합니다.

*(참고: 본 글의 jev-router 분석은 공개 소스 코드(`src/policy.mjs`, `config.mjs`), 공식 README, GitHub 공개 이슈 트래커를 바탕으로 한 정적 아키텍처 분석에 기반합니다.)*

## 1. jev-router는 어떻게 작동하는가

jev-router는 로컬 HTTP 프록시 형태로 동작하는 경량 모델 라우터입니다. 주로 대화형 코딩 CLI 도구(Claude Code, Codex CLI)의 API 호출을 중간에서 가로채(Interception) 처리하는 방식으로 설계되었습니다.

개발자가 CLI에서 프롬프트를 입력하면, 프록시가 매 대화 턴(turn)마다 프롬프트 텍스트를 외부 경량 분류기(TypeSafe API)로 보냅니다. 분류기가 해당 요청의 복잡도를 분석하여 티어를 판정하면, 프록시는 사전에 정의된 티어 매핑 규칙에 따라 요청 헤더와 페이로드의 모델 ID를 더 저렴한 모델로 교체하여 실제 공급자에게 전달합니다.

* **Claude 계열 티어 매핑**: `Fast`(Haiku) → `Balanced`(Sonnet) → `Strong`(Opus) / 긴 문맥용 `Long`(Fable, opt-in)
* **Codex 계열 티어 매핑**: `Fast`(Luna) → `Balanced`(Terra) → `Strong`(Sol) / 긴 문맥용 `Long`(Astra, opt-in)

기본 라우팅 사다리는 Fast-Balanced-Strong 3단계로 동작하며, 최상위 모델인 Fable과 Astra는 별도의 opt-in 설정을 통해서만 연결되는 구조입니다.

```text
[jev-router: 턴 단위 프록시 교체]
개발자 CLI 프롬프트 ──► 로컬 프록시 ──► 외부 TypeSafe 분류기 (복잡도 판정)
                            │
                            └─► 모델 ID 동적 교체 ──► 실제 LLM API

[우리 구조: 슬라이스 단위 명시 위임]
메인 에이전트 (상급 고정) ──► 독립 슬라이스 분할 ──► 오케스트레이터
                                                    ├─► 일반 작업자 A (모델 명시 고정 병렬)
                                                    └─► 일반 작업자 B (모델 명시 고정 병렬)
                                                            │
                                                            └─► 판단 필요 시 [에스컬레이션 반환]
```

### 인정할 만한 실무적 설계들

jev-router의 정책 구현부(`src/policy.mjs`)를 분석하면서 실무 환경을 고민한 흔적이 역력한 영리한 설계 패턴들을 확인할 수 있었습니다.

1. **단일 정책 응집**: 판정 기준과 안전장치, 티어 규칙이 `policy.mjs` 한 파일에 응집도 높게 작성되어 있어 룰을 파악하고 디버깅하기 쉽습니다.
2. **장애 허용(Fail-Open)**: 외부 분류기 API 호출이 실패하거나 확신도가 낮을 경우(`jev-unavailable`), 파이프라인을 멈추는 대신 직전 모델을 그대로 유지하여 개발 흐름이 끊기지 않도록 방어합니다.
3. **프롬프트 캐시 보존(Cache Preservation)**: 대화 컨텍스트가 길어진 상태에서 모델을 하향 변경하면 공급자 측의 프롬프트 KV 캐시가 무효화되어 오히려 레이턴시와 비용이 폭증합니다. jev-router는 누적 컨텍스트가 임계치를 넘으면 모델 다운그레이드를 거부하도록(`downgrade-not-worth-cache-rebuild`) 설계되어 있습니다.
4. **저신뢰도 상향 상한**: 분류기의 확신도가 낮을 때 무조건 최고가 모델로 점프하지 않고, 중간 밸런스 티어까지만 승격시키는 완충 장치(`uncertainCeiling`)를 두었습니다.
5. **툴 루프 세션 유지**: CLI 도구가 연속해서 도구를 실행하는 루프 구간에서는 티어가 시작 시점 모델로 유지되어 일관성을 보장합니다.

단일 개발자가 개인 터미널 세션에서 별도의 조작 없이 토큰 비용을 아끼고자 할 때, 이 도구는 분명 실용적인 아이디어를 제공합니다.

## 2. 우리가 도입하지 않기로 결정한 4가지 기술적 이유

그러나 개인의 단일 터미널 도구를 넘어, 여러 에이전트가 협업하고 예측 가능한 소프트웨어를 생산해야 하는 **엔지니어링 팀의 파이프라인 관점**에서 볼 때 jev-router는 명확한 한계와 리스크를 안고 있었습니다.

| 비교 항목 | jev-router 방식 | 우리의 오케스트레이션 아키텍처 |
|---|---|---|
| **제어 기본 단위** | 대화 턴(Turn) 단위 동적 교체 | 작업 슬라이스(Slice) 단위 명시 배정 |
| **최적화 목표** | 비용 절감 ("가장 싼 적정 모델") | 작업 적합성 ("필요한 추론 깊이에 부합하는 모델") |
| **동작 메커니즘** | 센티널(`AUTO_MODEL`) 기반 프록시 가로채기 | 오케스트레이터가 작업자별 모델을 명시 고정 |
| **적용 범위** | 특정 코딩 CLI 도구 한정 | 멀티 프로바이더 및 파이프라인 전반 |
| **판정 근거** | 외부 분류기의 단일 턴 텍스트 판정 | 실측 테스트 게이트(Quality Gate) 및 A/B 실측 |
| **외부 전송 데이터** | 매 턴 개발자 프롬프트 텍스트 | 과제 요약 1줄 수준의 최소 메타데이터 |
| **예외 발생 시 대응** | 직전 모델 유지 (Fail-Open) | 작업자의 명시적 에스컬레이션 반환(`[반환]`) |

### 이유 1. 표면 불일치: 라우터가 개입할 표면의 부재 (기능적 중복)

jev-router의 소스 코드(`src/config.mjs`)를 보면 세션 모델이 `AUTO_MODEL = "jev-router"` 센티널로 설정되어 있을 때만 동적 라우팅이 동작하며, 사용자가 구체적인 모델 ID를 명시하면 라우팅이 개입하지 않고 그대로 통과(Pass-through)합니다.

저희가 채택한 오케스트레이션 아키텍처에서는 메인 에이전트가 아키텍처와 명세를 설계하고, 서브에이전트를 띄울 때 **해당 작업의 성격에 맞춰 최적의 모델을 사전에 명시적으로 고정**합니다.
- 아키텍처 설계, 복합 판단, 코드 리뷰: 상급 추론 모델
- 확정된 인터페이스 구현, 정형 치환, 단위 테스트 작성: 일반 실행 모델

이처럼 작업자별로 모델이 이미 확정되어 있는 구조에서는 jev-router 센티널을 사용할 영역이 없습니다. 즉, 아키텍처 상 **라우터가 개입할 수 있는 표면 자체가 존재하지 않는 기능적 중복**입니다. 반대로 대화형 메인 세션에 이를 적용하기에는 아래에서 설명할 비공개 계약 리스크 대비 얻는 이득이 제한적입니다.

### 이유 2. 최적화 목표의 차이: "가장 싼 모델" vs "작업에 필요한 추론 깊이"

jev-router의 핵심 철학은 **"가장 싼 충분한 모델(Cheapest Sufficient Model)"**을 찾아 아래로 내려보내는 비용 사다리입니다.

하지만 실무 엔지니어링에서 토큰 몇 센트를 아끼려다 코드 버그를 만들어내면, 이를 디버깅하고 롤백하고 재작성하는 데 훨씬 큰 엔지니어링 비용(개발자 시간과 추가 API 토큰)이 소모됩니다. 

물론 jev-router도 캐시 보존이나 저신뢰도 상한 등 훌륭한 안전장치를 갖추고 있습니다. 그러나 턴 단위로 모델을 교체하는 방식의 본질적인 한계는 '기억 상실'이 아니라 **'복잡한 도메인 설계 맥락을 유지하고 검증하는 데 필요한 추론 역량(Capability)의 미스매치'**입니다. 대화 이력 자체는 새 모델에 전달되더라도, 복잡한 동시성 이슈나 숨은 제약 조건을 파악하는 추론 깊이가 모델마다 다르기 때문에 미묘한 설계 결함이 발생할 확률이 높아집니다.

저희가 추구하는 것은 "가장 싼 모델"이 아니라 **"작업에 필요한 추론 깊이(Reasoning Depth)에 정확히 부합하는 모델"**입니다.
- 원인 불명의 동시성 버그 디버깅, 복합 의사결정, 스키마 변경: **충분한 추론 능력을 갖춘 상급 모델**
- 이미 인터페이스와 입출력 명세가 확정된 정형 구현, 단순 치환: **비용 효율적인 일반 실행 모델**
- 문서화, 카피라이팅, 시각적 레이아웃: **해당 도메인에 특화된 모델**

어떤 모델이 어떤 작업에 적합한지는 마케팅성 벤치마크 점수로 판단하지 않습니다. 버그 상황을 재현하고 고치는 `Red-First` 테스트 픽스처 통과 여부, 그리고 실제 프로젝트의 빌드·diff·소요 시간으로 측정하는 **실측 품질 게이트(Quality Gate)**를 통과한 모델만을 해당 작업에 배정합니다.

### 이유 3. 프라이버시 및 컴플라이언스: 제3자 데이터 처리자 리스크

jev-router는 난이도 판별을 위해 개발자가 입력한 프롬프트 텍스트를 외부 분류기(TypeSafe API)로 보냅니다. 공식 README에 명시되어 있듯이 대화 이력 전체나 툴 출력은 보내지 않고 해당 턴의 프롬프트 텍스트만 전송되므로, 이를 '무단 전송'으로 볼 수는 없습니다.

하지만 엔터프라이즈 및 실무 개발 환경 관점에서 볼 때 본질적인 문제는 **데이터의 전송량 자체가 아니라, 제3자 데이터 처리자(Third-party Data Processor)를 파이프라인 중간에 추가하는 데서 오는 컴플라이언스 리스크**입니다.
1. 개발자가 프롬프트에 민감한 비즈니스 로직, 내부 설정, 기획 문서를 직접 복사해 붙여넣는 경우가 빈번합니다.
2. 주요 AI 공급자(Anthropic, OpenAI 등)와 체결한 엔터프라이즈 계약(데이터 미학습, 즉시 폐기 보장)과 달리, 외부 경량 분류기 서비스의 데이터 보존(Retention) 및 재학습 정책은 추가적인 검증이 필요합니다.

경량 분류기 자체는 호출당 비용이 매우 저렴($0.00014 수준)하여 매력적인 기술입니다. 그러나 이를 안전하게 활용하려면 프롬프트 원문 전문을 넘기는 것이 아니라, **"수행할 과제의 핵심 정의 1줄"** 수준으로 메타데이터를 최소화하여 보내는 격리 설계가 전제되어야 합니다.

### 이유 4. 비공개 계약 종속과 런타임 불안정성

jev-router는 공식 API 게이트웨이가 아니라, Claude Code나 Codex 같은 특정 CLI 도구의 내부 HTTP 트래픽을 가로채는 비공개 계약(Undocumented Contract)에 기생합니다.

이러한 도구들은 툴 자체의 마이너 업데이트나 통신 규격 변경 하나만으로도 예상치 못한 오동작을 일으킬 수 있습니다. 실제로 jev-router의 공개 이슈 트래커를 살펴보면 운영 환경에서 유의해야 할 사례들이 보고되어 있습니다.

## 3. 우리가 지향하는 대안: 슬라이스 위임과 그 트레이드오프

저희가 선택한 해답은 **"프롬프트 단위의 동적 바꿔치기"가 아니라, "명세 중심의 슬라이스 위임과 실측 기반의 오케스트레이션"**입니다.

```text
[슬라이스 위임 및 에스컬레이션 흐름]
1. 사용자 요구사항 접수
   │
2. 메인 에이전트 (상급 모델)
   ├─ 방향 설정 및 아키텍처 판단
   ├─ 파일 충돌 없는 독립 슬라이스 분할 (Disjoint File Ownership)
   └─ 성공 기준(테스트/타입) 명세화
   │
3. 슬라이스 작업자 (일반 모델) 병렬 실행
   ├─ 명세 기반 구현 및 자체 검증
   │
   ├─ [정상] ──► 변경 결과 요약 보고 ──► 메인이 통합 후 최종 검증
   │
   └─ [예외: 명세 밖 판단 필요 or 2회 연속 실패]
         │
         └─► [에스컬레이션 반환] ──► 메인 에이전트가 상향 재분류하여 해결
```

### 1. 생각의 양(추론 깊이)에 따른 역할 분리
파일 개수나 코드 라인 수가 아니라, **"이 작업에 주관적 판단이나 아키텍처 결정이 얼마나 남아있는가?"**를 기준으로 나눕니다.
- **판단형(상급 모델)**: 사용자 요구사항 조율, 아키텍처 설계, 멀티 에이전트 분할, 결과 검증.
- **실작업형(일반 모델)**: 명세가 확정된 코드 구현, 기계적 리팩토링, 정형화된 테스트 코드 작성.

### 2. 격리된 파일 소유권(Disjoint File Ownership) 기반 슬라이스 병렬 위임
메인 에이전트는 직접 모든 코드를 작성하지 않습니다. 작업을 파일 수정 영역(`write_set`)이 겹치지 않는 독립 슬라이스로 쪼갠 뒤, 하위 작업자들에게 병렬로 위임합니다. 하위 작업자들은 이미 모델과 역할이 명확히 고정되어 있으므로 불확실한 프록시 라우팅에 의존할 필요가 없습니다.

### 3. 명확한 에스컬레이션 반환 프로토콜 (`[반환]`)
하위 작업자(일반 모델)가 작업을 수행하다가 명세에 없는 모호한 결정을 내려야 하거나, 동일한 에러로 2회 이상 연속 실패하면 **자의적으로 코드를 고치지 못하도록 강제**합니다. 즉시 `[반환]` 신호를 띄우고 지금까지 확인한 사실과 남은 선택지를 메인 에이전트에 보고하며 멈춥니다. 

메인 에이전트는 이 신호를 받아 직접 고성능 추론으로 해결하거나 상향 재분류를 진행합니다. 이 프로토콜 덕분에 저렴한 모델을 쓰면서도 발생할 수 있는 품질 붕괴를 조기에 방어할 수 있습니다.

### 솔직한 트레이드오프: 슬라이스 위임의 비용

슬라이스 위임이 모든 상황에서 만능인 것은 아닙니다. 이 방식 역시 명확한 비용과 오버헤드가 발생합니다:

1. **브리핑 및 오케스트레이션 토큰 오버헤드**: 메인 에이전트가 하위 작업자에게 작업을 전달하기 위해 명세를 작성하고 컨텍스트를 요약하는 과정에서 추가 토큰이 소모됩니다.
2. **컨텍스트 재적재(KV Cache 미공유)**: 독립된 세션으로 작업자를 띄우기 때문에 메인 세션의 프롬프트 캐시를 재활용하지 못하고 기본 컨텍스트를 다시 로드해야 합니다.
3. **직렬 계획 레이턴시**: 작업을 쪼개고 검증하는 계획 단계가 선행되어야 하므로, 즉각적인 응답이 필요한 상황에서는 단일 대화 세션보다 체감 속도가 느릴 수 있습니다.

따라서 **단순 1~2개 파일의 가벼운 수정이나, 파일 간 의존성이 너무 강해 쪼개기 어려운 작업**에서는 슬라이스 위임을 하지 않고 메인 세션이 직접 처리하는 것이 비용과 속도 측면 모두에서 훨씬 효율적입니다.

## 4. 정리하며: 기술 선택의 기준선

오픈소스 프로젝트인 `jev-router`는 단일 터미널 세션에서 개발하는 개인에게 신선한 접근법을 제시한 훌륭한 시도입니다. 특히 캐시 보존을 고려한 설계(`downgrade-not-worth-cache-rebuild`)나 Fail-Open 정책 등은 라우팅 시스템을 고민하는 모든 엔지니어에게 유익한 레퍼런스가 됩니다.

하지만 **신뢰성과 보안, 그리고 예측 가능성이 최우선인 팀 단위 엔지니어링 파이프라인**에서는 다음과 같은 원칙이 중요합니다.

1. **비용 절감은 아키텍처의 부산물이어야 한다**: 무조건 싼 모델로 깎아내리는 것은 국소 최적화에 불과합니다. 명확한 인터페이스 분리와 작업 슬라이싱이 선행될 때 비로소 품질 저하 없는 비용 절감이 가능합니다.
2. **비공개 계약에 기생하는 프록시의 유지보수 비용을 고려한다**: CLI 마이너 업데이트로 무력화되거나 런타임 에러를 유발할 수 있는 비공식 프록시는 지속 가능한 인프라로 채택하기에 리스크가 큽니다.
3. **도구의 아이디어는 흡수하되, 파이프라인 규범에 맞게 내재화한다**: 경량 분류기나 캐시 보호 로직 같은 유용한 개념은 취하되, 프롬프트 원문을 보호하고 오케스트레이터의 통제권 아래 두는 것이 더 견고한 엔지니어링 방향입니다.

OpenRouter를 쓰지 않는 환경에서도 모델 비용 최적화의 본질은 "가장 싼 모델 찾기"가 아니라 **"적합한 추론의 깊이를 적재적소에 명시적으로 배치하는 것"**에 있다는 점을 이번 분석을 통해 확인할 수 있었습니다.

## 자주 묻는 질문 (FAQ)

### Q. OpenRouter를 쓰지 않는 환경에서 모델 비용 최적화는 어떻게 시작해야 할까요?
가장 먼저 해야 할 일은 '대화 전체를 무조건 최상위 모델 하나로 처리하는 습관'을 버리는 것입니다. 아키텍처 설계 단계와 구현 단계를 분리하세요. 구현 명세와 테스트 코드가 확정된 작업은 비용 효율적인 일반 모델에 명시적으로 위임하고, 자체 검증을 거치게 하는 파이프라인을 구축하는 것만으로도 불필요한 고비용 모델 남용을 방지하고 예측 가능한 비용 관리가 가능해집니다.

### Q. 턴 단위 라우팅 프록시가 유효한 유스케이스는 전혀 없나요?
개인 개발자가 토이 프로젝트나 개인 탐색 목적으로 단일 터미널에서 작업할 때는 유용할 수 있습니다. 다만 이 경우에도 CLI 도구가 업데이트될 때 라우팅이 정상 작동하는지 수시로 확인해야 하며, 프롬프트 텍스트가 외부 분류기로 전달된다는 점을 인지하고 있어야 합니다.

### Q. 슬라이스 위임 방식에서 하위 작업자가 실패하면 어떻게 하나요?
하위 작업자가 스스로 억지 수정을 반복(Looping)하지 못하도록 '2회 실패 시 즉시 반환' 같은 명확한 에스컬레이션 프로토콜을 둡니다. 상위 에이전트가 반환된 컨텍스트와 시도 결과를 검토하여 직접 해결하거나 명세를 보완해 재위임하므로, 품질 붕괴를 조기에 방어할 수 있습니다.
